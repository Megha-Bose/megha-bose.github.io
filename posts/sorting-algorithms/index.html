Sorting Algorithms - How Order Turns Hard Problems Easy

Aug 2021
9 min read

Helpful context:

  • Data Structures - Storage Is Strategy

In 1945 John von Neumann wrote one of the very first programs for a stored-program computer, the EDVAC. It was a merge sort. Sorting has been at the center of computing ever since: database indexes, ranked search results, directory listings and compression all depend on it. Usually sorting isn’t the goal. It’s the step that makes the real goal easy.

At 16 items the counts are close, and simple insertion sort holds its own. Scale up and the differences explode: on 10,000 shuffled items, insertion sort averages about 25 million comparisons, while merge sort needs around 130,000.

Why Sorting Unlocks Everything

Sorted data turns slow questions into fast ones:

  • Search drops from $O(n)$ to $O(\log n)$ with binary search .
  • Duplicates end up next to each other, so one pass finds them all.
  • Merging two sorted lists takes $O(n)$, and so do database joins on sorted keys.
  • Medians, percentiles and ranges become a matter of reading off a position.

The Comparison Lower Bound

Before writing any code: how fast can sorting possibly be?

Most sorts learn about the order only by asking yes/no questions: “is $a > b$?” Each of the $n!$ possible orderings of the input needs a different set of moves to sort, so each must produce a different sequence of answers. If two orderings got identical answers, the algorithm would treat them identically and get at least one wrong. $k$ yes/no answers can tell apart at most $2^k$ cases, so

$$2^k \geq n! \quad\Longrightarrow\quad k \geq \log_2(n!) \approx n \log_2 n$$

That last step is intuitive: $\log(n!) = \log 1 + \log 2 + \cdots + \log n$, and most of those $n$ terms are close to $\log n$. So no comparison-based sort can beat $\Omega(n \log n)$ comparisons in the worst case. Merge sort and heap sort hit that bound, so they’re optimal in this model.

The exact estimate, via Stirling's approximation

Stirling’s approximation, $n! \approx \sqrt{2\pi n},(n/e)^n$, gives $\log_2(n!) \approx n \log_2 n - n \log_2 e$, which is $\Theta(n \log n)$.

Insertion Sort: Simple and Surprising

Sort the way you sort a hand of cards: take one card at a time and slide it left until it fits among the cards you already hold.

Worst case, on reverse-sorted input, every card slides all the way: $1 + 2 + \cdots + (n-1) = O(n^2)$. But if every element starts within $k$ places of where it belongs, it costs only $O(kn)$. On nearly-sorted data it’s linear, and nothing beats it:

This is an interactive animation. It needs JavaScript to run.

That’s why the fast sorts used in real libraries hand small or nearly-sorted pieces over to insertion sort.

Code: insertion sort, and bubble sort for comparison 
def insertion_sort(arr):
    for i in range(1, len(arr)):
        key = arr[i]
        j = i - 1
        while j >= 0 and arr[j] > key:
            arr[j + 1] = arr[j]
            j -= 1
        arr[j + 1] = key

Bubble sort repeatedly swaps adjacent elements that are out of order, so the largest “bubbles” to the end on each pass. It’s also $O(n^2)$, stable and in place, but every swap costs three assignments where insertion sort shifts once. It’s taught for its simplicity; there’s no practical reason to use it.

def bubble_sort(arr):
    n = len(arr)
    for i in range(n):
        swapped = False
        for j in range(n - 1 - i):
            if arr[j] > arr[j + 1]:
                arr[j], arr[j + 1] = arr[j + 1], arr[j]
                swapped = True
        if not swapped:          # no swaps: already sorted, stop early
            break

Merge Sort: Divide, Conquer, Combine

  1. Split the array in half.
  2. Sort each half, recursively.
  3. Merge the two sorted halves: compare their front elements, take the smaller, repeat.

Merging is $O(n)$, and halving gives $\log n$ levels, so

$$T(n) = 2T(n/2) + O(n) = \Theta(n \log n)$$

on every input. That’s case 2 of the Master Theorem .

Merge sort is stable: equal elements keep their original order. That matters when sorting by several keys: sort by name, then stably by date, and names stay alphabetical within each date. The cost is $O(n)$ extra memory for the merge.

Code: merge sort 
def merge_sort(arr):
    if len(arr) <= 1:
        return arr
    mid = len(arr) // 2
    left, right = merge_sort(arr[:mid]), merge_sort(arr[mid:])
    result, i, j = [], 0, 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]:            # <= keeps it stable
            result.append(left[i]); i += 1
        else:
            result.append(right[j]); j += 1
    return result + left[i:] + right[j:]

Quicksort: Fast, But Not Guaranteed

Pick a pivot. Move everything smaller to its left and everything larger to its right, and the pivot is now in its final place. Repeat on each side.

If pivots split the array roughly in half, that’s $O(n \log n)$. If a pivot is always the smallest or largest value, each round peels off just one element and the total is $O(n^2)$. The second case in the animation above shows exactly that: always picking the last element, on input that’s already sorted.

The fix is a random pivot. Then no particular input is bad, and the expected time is $O(n \log n)$ whatever you feed it.

“Why does everyone use an algorithm with an $O(n^2)$ worst case?" Three reasons. With random pivots, the bad case is astronomically unlikely. Real implementations also watch the recursion depth and switch to heap sort if it grows suspiciously deep; this hybrid is called introsort, and it guarantees $O(n \log n)$. And quicksort sorts in place, scanning memory in order, which the cache rewards, so on random data it’s often noticeably faster than merge sort.

Code: quicksort with a random pivot 
import random

def quicksort(arr, lo=0, hi=None):
    if hi is None:
        hi = len(arr) - 1
    if lo < hi:
        p = partition(arr, lo, hi)
        quicksort(arr, lo, p - 1)
        quicksort(arr, p + 1, hi)

def partition(arr, lo, hi):
    r = random.randint(lo, hi)
    arr[r], arr[hi] = arr[hi], arr[r]          # random pivot, moved to the end
    pivot, i = arr[hi], lo - 1
    for j in range(lo, hi):
        if arr[j] <= pivot:
            i += 1
            arr[i], arr[j] = arr[j], arr[i]
    arr[i + 1], arr[hi] = arr[hi], arr[i + 1]  # pivot into its final place
    return i + 1

Heap Sort: Guaranteed, and In Place

Heap sort first arranges the array into a max-heap, a tree stored in the array where every parent is at least as large as its children, so the maximum sits at the front. Building it takes $O(n)$ (here’s why ). Then, $n$ times: swap the maximum to the end, and let the new front element sink back down to restore the heap in $O(\log n)$.

That’s $O(n \log n)$ on every input with $O(1)$ extra memory: a guarantee with no randomness, and the reason introsort falls back on it. The downsides: it isn’t stable, and jumping between parent and child positions is hard on the cache, so in practice it’s slower than quicksort.

Code: heap sort 
def sift_down(arr, i, n):
    # push node i down until it is at least as large as both children
    largest = i
    left, right = 2 * i + 1, 2 * i + 2
    if left < n and arr[left] > arr[largest]:
        largest = left
    if right < n and arr[right] > arr[largest]:
        largest = right
    if largest != i:
        arr[i], arr[largest] = arr[largest], arr[i]
        sift_down(arr, largest, n)

def heap_sort(arr):
    n = len(arr)
    for i in range(n // 2 - 1, -1, -1):   # build the max-heap in O(n)
        sift_down(arr, i, n)
    for end in range(n - 1, 0, -1):
        arr[0], arr[end] = arr[end], arr[0]   # move the max to the end
        sift_down(arr, 0, end)                # restore the heap

Counting Sort and Radix Sort: Beating the Lower Bound

The $\Omega(n \log n)$ bound only covers sorts that compare. If you know something about the keys, you can skip comparing altogether.

  • Counting sort: keys are integers in a small range $[0, k)$. Count how often each value appears, then write them out in order: $O(n + k)$.
  • Radix sort: sort fixed-width integers one digit at a time, least significant digit first, using a stable sort for each digit. With $d$ digits in base $b$, that’s $O(d \cdot (n + b))$. For 32-bit integers taken a byte at a time, $d = 4$ and $b = 256$: linear time.

The catch is that the keys need that structure. Neither works for arbitrary comparison keys, and both need $O(n)$ extra memory.

Code: counting sort and radix sort 
def counting_sort(arr, k):
    count = [0] * k
    for x in arr:
        count[x] += 1
    return [x for x, freq in enumerate(count) for _ in range(freq)]

def radix_sort(arr):
    exp = 1
    while max(arr) // exp > 0:
        buckets = [[] for _ in range(10)]
        for x in arr:
            buckets[(x // exp) % 10].append(x)   # stable: keeps earlier order
        arr = [x for bucket in buckets for x in bucket]
        exp *= 10
    return arr

Timsort: What Python Actually Uses

Python’s sort and Java’s sort for objects use Timsort, a hybrid built for real-world data, which is rarely random. It often contains runs that are already sorted, or sorted backwards.

Timsort scans for those runs, flips the reversed ones, extends short runs with insertion sort, and merges runs in a careful order that guarantees $O(n \log n)$. Already-sorted input is a single run: $O(n)$. On partly ordered data, it regularly beats pure quicksort.

arr.sort()               # in place, Timsort
sorted_arr = sorted(arr) # returns a new sorted list
