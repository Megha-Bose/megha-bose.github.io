Big-O - Why the Right Algorithm Beats Faster Hardware

Try making the supercomputer 100,000 times faster. It buys a lead at small sizes, then loses anyway. Faster hardware multiplies your speed by a constant. A better algorithm changes the shape of how the work grows, and shape always wins in the end.

Big-O is the language for that shape. It doesn’t care about microseconds or clock cycles. It asks one question: as the input grows, how does the work grow with it?

What Does “Fast” Mean?

Look up a name in a sorted phone book. You can read from the first page, or open the middle and throw away the half that can’t contain it.

This is an interactive demo. It needs JavaScript to run.

Both methods are correct. The difference is the shape:

  • Reading in order does about $n$ steps for $n$ entries. Double the book and the work doubles. That’s $O(n)$.
  • Halving does about $\log_2 n$ steps. Double the book and it needs one more step. That’s $O(\log n)$.

At a million entries that’s a million steps against twenty. We always call the input size $n$.

Drop the Clutter

Suppose an algorithm does exactly $3n^2 + 7n + 12$ steps. Big-O calls that $O(n^2)$: it keeps the biggest term and throws away its constant. Slide $n$ and you can see why.

This is an interactive demo. It needs JavaScript to run.
  • Lower-order terms vanish. Past a few hundred, $7n + 12$ is a rounding error next to $3n^2$.
  • Constants describe the machine, not the method. A computer twice as fast turns $3n^2$ into $1.5n^2$. It’s still a parabola, and it still grows by four times when $n$ doubles.

The Common Complexity Classes

The fastest way to feel a complexity class is to double the input and see what happens to the work.

“But my $O(n^2)$ code beats their $O(n \log n)$ code!" For small $n$ it can, and often does. If the $O(n \log n)$ version spends 100 steps where the $O(n^2)$ version spends one, the simple method wins until $n$ is in the hundreds. Past the crossover, the better shape wins at every size, however big the constant. The first demo on this page is that crossover, with the constant played by hardware. Benchmarks exist to tell you which side of the crossover your real $n$ is on.

The Formal Definition, Made Visible

“Grows no faster than” has a precise meaning:

$f(n) = O(g(n))$ when there are constants $c > 0$ and $n_0$ such that

$$f(n) \leq c \cdot g(n) \text{ for all } n \geq n_0$$

In words: past some starting point $n_0$, a scaled-up copy of $g$ stays on top of $f$ forever. Proving $f(n) = O(g(n))$ just means finding one $c$ and one $n_0$ that work. Find them yourself:

Notice the two escape hatches. $n_0$ lets you ignore small inputs, where the clutter still matters. $c$ lets you ignore constant factors. But no choice of $c \leq 3$ ever works, because $3n^2 + 7n + 12$ is always more than $3n^2$. That’s the definition doing its job: it tolerates constants, not a bigger shape.

The full family: O, o, Ω, ω and Θ

Big-O, $O(g(n))$, a loose upper bound. $f(n) \leq c \cdot g(n)$ for some $c$ and all $n \geq n_0$. $f$ grows no faster than $g$.

Little-o, $o(g(n))$, a strict upper bound. For every $c > 0$ there is an $n_0$ with $f(n) < c \cdot g(n)$ for all $n \geq n_0$. $f$ grows strictly slower than $g$. So $\log n = o(n)$, but $n \neq o(n)$. Every $o$ is also an $O$, but not the other way round.

Big-Omega, $\Omega(g(n))$, a loose lower bound. $c \cdot g(n) \leq f(n)$ for some $c$ and all $n \geq n_0$. $f$ grows at least as fast as $g$.

Little-omega, $\omega(g(n))$, a strict lower bound. For every $c > 0$, eventually $c \cdot g(n) < f(n)$. $f$ grows strictly faster than $g$. So $n^2 = \omega(n)$, but $n \neq \omega(n)$.

Big-Theta, $\Theta(g(n))$, a tight bound. Both $O(g(n))$ and $\Omega(g(n))$: $f$ grows exactly as fast as $g$. There is no “little theta”, since nothing can be strictly above and strictly below $g$ at once.

In casual use people say $O$ when they mean $\Theta$. “Merge sort is $O(n \log n)$” is true, but so is “merge sort is $O(n^5)$”. $\Theta(n \log n)$ is the precise statement.

If an algorithm is… it means
$O(n)$ at most linear, possibly faster: a ceiling
$o(n)$ strictly faster than linear, like $\log n$
$\Omega(n)$ at least linear: a floor
$\omega(n)$ strictly slower than linear, like $n^2$
$\Theta(n)$ exactly linear

Worst, Average, and Best Case

Big-O describes how work grows with $n$. But for one fixed $n$, different inputs can cost very different amounts. In the phone book race, picking a few targets shows it: reading in order sometimes wins in one step and sometimes needs all 64.

  • Best case: the luckiest input. The target is first: $O(1)$.
  • Worst case: the input that forces the most work. The target is last, or missing: $O(n)$. This is the usual one to quote, because it’s a guarantee.
  • Average case: the expected cost over random inputs. On average you read half the list: $O(n/2) = O(n)$.

Averages matter when choosing between algorithms. Quicksort’s worst case is $O(n^2)$, but its average is $O(n \log n)$, and with random pivots the worst case practically never happens. That’s why it’s the default sort in so many libraries.

Amortized Thinking: Expensive Steps That Are Rare

Some operations are usually cheap and occasionally very expensive. If the expensive ones are rare enough, the average over the whole sequence is still cheap. The classic example is a dynamic array, like a Python list or a C++ vector.

This is an interactive demo. It needs JavaScript to run.

Each copy costs as much as everything pushed so far. But copies happen only at sizes 1, 2, 4, 8, and so on, so all the copying put together adds up to less than $2n$. Spread over $n$ pushes, that’s under 3 steps each. We say a push is $O(1)$ amortized. That’s a promise about the sequence, not about any single push: one unlucky push really can take $O(n)$. Amortized Analysis covers the general technique.

Recurrences: Where Divide-and-Conquer Spends Its Time

Divide-and-conquer algorithms split a problem into smaller copies of itself. Merge sort sorts two halves, then merges them in $O(n)$:

$$T(n) = 2T(n/2) + O(n)$$

The way to solve this is to draw the recursion tree, where each level is one round of splitting, and add up the work level by level. Choose an algorithm, or set your own $a$, $b$ and $c$:

For merge sort every level does the same $O(n)$ work, and halving $n$ until it reaches 1 takes $\log_2 n$ levels. So the total is $O(n \log n)$.

The Master Theorem

The tree above has only three possible shapes, and the Master Theorem names them. For

$$T(n) = a \cdot T(n/b) + O(n^c)$$

each level does $r = a / b^c$ times the work of the level above it. Everything depends on whether $r$ is below, equal to, or above 1. That’s the same as comparing $c$ with the critical exponent $\log_b a$.

Case Condition Where the work is Result Example
1 $c < \log_b a$ ($r > 1$) the leaves $\Theta(n^{\log_b a})$ Strassen, $a=7, b=2, c=2$: $\Theta(n^{2.807})$
2 $c = \log_b a$ ($r = 1$) every level equally $\Theta(n^c \log n)$ Merge sort, $a=2, b=2, c=1$: $\Theta(n \log n)$
3 $c > \log_b a$ ($r < 1$) the root $\Theta(n^c)$ $a=2, b=4, c=1$: $\Theta(n)$

Every preset in the demo lands in one of these rows. Karatsuba’s multiplication is case 1, giving $\Theta(n^{1.585})$. Binary search is case 2 with $c = 0$, giving $\Theta(\log n)$.

Why the Master Theorem is true

At depth $k$ of the recursion tree there are $a^k$ subproblems, each of size $n / b^k$, each doing $(n/b^k)^c$ work. So level $k$ does

$$a^k \cdot \left(\frac{n}{b^k}\right)^c = n^c \cdot \left(\frac{a}{b^c}\right)^k = n^c \cdot r^k$$

The levels form a geometric series with ratio $r$:

  • $r < 1$ (so $c > \log_b a$): each level is smaller than the last. The series converges and the root’s $n^c$ dominates: $\Theta(n^c)$. Strictly, this case also needs a mild regularity condition on the work function, which polynomials satisfy.
  • $r = 1$ (so $c = \log_b a$): every one of the $\log_b n$ levels does $n^c$: $\Theta(n^c \log n)$.
  • $r > 1$ (so $c < \log_b a$): each level is bigger than the last, and the leaves dominate. There are $a^{\log_b n} = n^{\log_b a}$ leaves: $\Theta(n^{\log_b a})$.

The critical exponent $\log_b a$ compares how fast the number of subproblems grows (that’s $a$) with how fast each one’s cost shrinks (that’s $b^c$). Whichever side wins decides where the work concentrates.

Big-O gives the shape of the curve, not an exact step count. Shape is what decides whether a program finishes on a laptop or outlives the universe, and no amount of hardware changes the shape.
