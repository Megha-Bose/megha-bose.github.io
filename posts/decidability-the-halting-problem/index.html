Decidability & The Halting Problem - Questions No Program Can Answer

Aug 2021
6 min read

Helpful context:

  • Turing Machines - The Minimal Model of Everything a Computer Can Do

In 1936 Turing proved that no program can take any program $P$ and input $X$ and correctly answer: will $P(X)$ eventually halt, or run forever?

This isn’t a hardware limit or a gap in today’s mathematics. No computer that will ever exist can do it. That’s the halting problem, and seeing why it’s impossible changes how you think about what software can know about software.

Decidable vs. Recognizable

Two definitions do all the work:

  • A language $L$ is decidable if some Turing machine, on every input, eventually halts with the right answer: accept if the input is in $L$, reject if not. A decider always answers.
  • A language is recognizable (semi-decidable) if some machine accepts exactly the strings in $L$. On anything else it may reject, or run forever. A recognizer can leave you waiting for an answer that never comes.

Every decidable language is recognizable, but not the other way round. Sorting, graph reachability and primality testing are all decidable: comfortable problems that algorithms fully solve.

The Halting Problem

$$HALT = \{\langle M, w \rangle : M \text{ is a TM that halts on input } w\}$$

Here $\langle M, w \rangle$ is the machine and its input written out as one string, which the universal Turing machine showed is always possible.

$HALT$ is recognizable: simulate $M$ on $w$, and accept if it halts. If $M$ runs forever, so does the simulation, which a recognizer is allowed to do. But $HALT$ is not decidable. Here’s why, as a picture first:

The Proof, Step by Step

Assume a machine $H$ decides $HALT$: given any $\langle M, w \rangle$, it always halts, accepting if $M$ halts on $w$ and rejecting if it loops.

Build a machine $D$. On input $\langle M \rangle$:

  1. Run $H$ on $\langle M, \langle M \rangle \rangle$: does $M$ halt when fed its own description?
  2. If $H$ says it halts, loop forever.
  3. If $H$ says it loops, halt.

Ask what $D$ does on its own description $\langle D \rangle$:

  • If $D$ halts on $\langle D \rangle$, then $H$ accepted, so step 2 makes $D$ loop. Contradiction.
  • If $D$ loops on $\langle D \rangle$, then $H$ rejected, so step 3 makes $D$ halt. Contradiction.

Both cases are impossible, so $H$ can’t exist. It’s the liar’s paradox (“this sentence is false”) made rigorous: $D$ is built to do the opposite of whatever is predicted about it.

Why Diagonalization Works

This is Georg Cantor’s trick from 1891, used to prove there are more real numbers than whole numbers. Suppose you could list every real number between 0 and 1. Build a new number whose $n$-th digit differs from the $n$-th digit of the $n$-th number on the list. It differs from every entry somewhere, so it isn’t on the list, and the list wasn’t complete after all.

The animation is the same move. Take a supposedly complete table, walk down its diagonal, and flip every entry. What you build can’t be any row.

The link runs deeper. There are only countably many Turing machines, since each is a finite string, but uncountably many problems, since there are as many sets of strings as there are real numbers. So almost every problem is undecidable. The ones we can solve are a thin, countable sliver of an uncountable space.

Gödel's incompleteness theorems: the same idea, five years earlier

In 1931 Kurt Gödel used the same self-reference to shake the foundations of mathematics.

A formal system is a set of axioms plus rules of inference: a machine for producing proofs. Gödel’s first insight was to encode every formula and every proof as a natural number, so statements about arithmetic can talk about other statements, including themselves. That’s the formal version of a program reading its own code.

First incompleteness theorem. Any consistent formal system $F$ strong enough to express basic arithmetic contains a sentence $G_F$, roughly “this sentence is not provable in $F$”, that $F$ can’t prove. If $F$ proved $G_F$, it would prove a falsehood, contradicting consistency. So $G_F$ is unprovable, which is exactly what it says, so it’s true. (Showing that $F$ can’t disprove $G_F$ either needs a slightly stronger assumption, which Rosser later removed with a cleverer sentence.)

Second incompleteness theorem. No such system can prove its own consistency.

The connection to halting. The two results are close cousins. If halting were decidable, provability would be too: to check whether a statement is provable, run a program that searches through every possible proof, and ask whether it halts. Since halting is undecidable, no fixed set of axioms can settle every true statement of the form “this program halts”. Both arguments build a self-referential object that does the opposite of what a supposedly complete procedure predicts.

No consistent system powerful enough for arithmetic is complete, and better axioms can’t fix that.

Reductions: Spreading Undecidability

Once one problem is known to be undecidable, others follow without new diagonal arguments, through reductions. A reduction from $A$ to $B$ is a computable transformation $f$ with $x \in A \iff f(x) \in B$. If $B$ were decidable, $f$ would let us decide $A$. So if $A$ is undecidable, $B$ must be too.

Example: is a machine’s language empty? Take $E_{TM} = \{\langle M \rangle : L(M) = \emptyset\}$, and reduce the acceptance problem $A_{TM} = \{\langle M, w \rangle : M \text{ accepts } w\}$ to it.

Given $\langle M, w \rangle$, build a machine $M'$ that ignores its own input, runs $M$ on $w$, and accepts if $M$ does. Then $M'$ accepts everything if $M$ accepts $w$, and nothing otherwise. So $M$ accepts $w$ exactly when $L(M')$ isn’t empty. A decider for emptiness would therefore decide $A_{TM}$, which is undecidable, so emptiness is undecidable too.

Rice’s Theorem

That kind of reduction works for almost every question you’d want to ask about a program’s behavior. Rice’s theorem says it always does:

Any non-trivial property of what a program computes is undecidable.

Non-trivial means some programs have the property and some don’t. What a program computes means it depends only on the program’s input-output behavior, not on how it’s written. So all of these are undecidable:

  • Does this program accept any input at all? Every input? The empty string?
  • Does it terminate on every input?
  • Does it compute the same function as that other program?
  • Does it ever print “hello”?

“Then how do linters, type checkers and verifiers work?" They answer easier questions. Some accept false alarms, flagging code that’s actually fine. Some accept misses. Some restrict themselves to program classes where the question is decidable: bounded loops, simple arithmetic, or type systems that guarantee termination. Perfect program analysis is impossible; useful program analysis is everywhere.

Summary

Class Meaning Example
Decidable A machine always halts with the right answer Graph reachability, primality
Recognizable A machine accepts exactly the members, but may loop on the rest $HALT$, $A_{TM}$
Co-recognizable The complement is recognizable $\overline{HALT}$, $E_{TM}$
Neither Not recognizable, and neither is its complement $EQ_{TM}$: do two machines accept the same language?

A language is decidable exactly when it’s both recognizable and co-recognizable: run both machines side by side, and one of them must eventually answer. $HALT$ is recognizable but not decidable, so its complement can’t even be recognized.
