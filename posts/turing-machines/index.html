Turing Machines - The Minimal Model of Everything a Computer Can Do

Aug 2021
6 min read

Helpful context:

  • Automata Theory - What Machines Can and Cannot Compute
  • Context-Free Grammars - Languages With Recursive Rules

In 1928 David Hilbert asked whether there’s a mechanical procedure that can take any mathematical statement and decide whether it’s provable: the Entscheidungsproblem. Could mathematics itself be automated?

In 1936 a 24-year-old Alan Turing answered no. To do it he first had to pin down what “mechanical procedure” even means, so he invented the simplest machine he could: a tape, a read/write head, and a short list of rules. That bare machine turned out to compute anything that can be computed at all. We still use his definition. Whenever someone calls a problem unsolvable, or an algorithm polynomial-time, they’re talking about Turing machines.

The Machine

An infinitely long tape is divided into cells, each holding one symbol or a blank ($\sqcup$). A head sits on one cell. A finite control is in one of a few states. Every step, the machine:

  1. reads the symbol under the head,
  2. writes a symbol in its place (possibly the same one),
  3. moves one cell left or right,
  4. switches to a new state.

That’s the whole machine. It halts when it reaches the accept or reject state, and if it never reaches either, it runs forever. Here’s one at work:

The rules it follows are just a table: “in state q1 reading b: write Y, move right, go to q2." Six working states and eighteen rules, and it decides a language that no pushdown automaton can.

Formally, a Turing machine is a 7-tuple $M = (Q, \Sigma, \Gamma, \delta, q_0, q_\text{accept}, q_\text{reject})$, where $\Gamma$ is the tape alphabet including the blank, and the transition function $\delta: Q \times \Gamma \to Q \times \Gamma \times \{L, R\}$ maps a state and a symbol to a new state, a symbol to write, and a direction. A configuration - state, tape contents, head position - captures everything about a moment of the computation, and a run is just a sequence of configurations.

Why This Beats a Pushdown Automaton

$\{a^n b^n c^n\}$ is not context-free : a stack can match the $a$’s against the $b$’s, but then the count is gone and there’s nothing left to check the $c$’s against.

The Turing machine above doesn’t need to remember a count, because it writes on its own input. It crosses off one of each letter per round, walks back, and repeats. A tape it can read, rewrite and move along in both directions is working memory with no limit, and that’s the whole difference.

The Church-Turing Thesis

Finite automata recognize regular languages, pushdown automata context-free ones, and Turing machines strictly more. Is there anything more powerful still?

The Church-Turing thesis says no: anything that can be computed by any reasonable physical process can be computed by a Turing machine. It isn’t a theorem and can’t be, since “reasonable physical process” isn’t a mathematical object. But every model anyone has proposed computes exactly the same functions: Church’s lambda calculus from the same year, register machines, cellular automata, the RAM model, and quantum computers.

That’s what makes impossibility results so powerful. To show no algorithm can solve a problem, it’s enough to show no Turing machine can.

“Don’t quantum computers break this?" No. Shor’s algorithm factors integers exponentially faster than any known classical method, but a classical Turing machine can factor too, just slowly. Quantum computers compute the same functions, sometimes much faster. What they threaten is the Extended Church-Turing thesis, the claim that polynomial time means the same thing on every reasonable machine. That’s a separate claim.

Variants: Fancier Machines, Same Power

  • Multi-tape machines give each of $k$ tapes its own head: one for input, one for scratch work, one for output. Much easier to program, but a single-tape machine can simulate one with at most a quadratic slowdown, $O(t^2)$ for $t$ steps.
  • Nondeterministic machines may branch into several possible next steps, accepting if any branch accepts. A deterministic machine can simulate this with a breadth-first search over all the branches. It can be exponentially slower, but it recognizes the same languages.
  • Probabilistic machines flip coins at each step. Same languages again.

Bolt on any of these extras and the set of solvable problems stays exactly the same. That robustness is a big part of why the definition is so convincing: it doesn’t depend on hardware details.

The Universal Turing Machine

The idea that changed everything: a Turing machine’s rule table is just a finite string of symbols, so it can be written onto another machine’s tape. The Universal Turing Machine reads a description of any machine $M$ plus an input $w$, and simulates $M$ running on $w$. It accepts if $M$ accepts, rejects if $M$ rejects, and runs forever if $M$ does.

Before this, a machine’s program was its wiring; to change what it computed, you physically rebuilt it. Turing showed the program could be data. Every computer you’ve used, from your phone to a supercomputer, is a physical universal Turing machine. Your CPU reads machine-code instructions out of memory and carries them out, exactly as the UTM reads a rule table off its tape.

What "a program as input" actually means, with a tiny example

A machine $M$ is fully described by its rule table, a finite list of “in state $q$ reading $s$: write $s'$, move, go to $q'$”. Written out as text, that table is an ordinary input string.

Take a two-rule machine: in $q_0$ reading 0, accept; in $q_0$ reading 1, reject. Encode it as (q0,0,ACCEPT)(q0,1,REJECT), put a separator # after it, then the real input:

(q0,0,ACCEPT)(q0,1,REJECT) # 0

The UTM reads everything before # and learns the two rules. Then it moves to the input, sees 0, and looks up what its simulated machine does in state $q_0$ reading 0: accept. With input 1 it would reject. The UTM never knew anything about 0 or 1; it learned that behavior by reading $M$’s description.

That’s exactly python script.py. The interpreter has no idea what your script does until it reads the file. Code is just a particular kind of data, and one general-purpose machine can run any program you give it.

The UTM also powers the diagonal argument that makes the halting problem undecidable, which is the next post.

Summary

Machine Memory Can recognize, for example
Finite automaton A fixed set of states $\{w : w \text{ contains } 01\}$
Pushdown automaton One stack $\{0^n 1^n : n \geq 0\}$
Turing machine An unbounded tape it can rewrite $\{a^n b^n c^n : n \geq 0\}$

The Turing machine is our model of what computation is. Multi-tape, nondeterministic and probabilistic variants all recognize the same languages, though their speeds differ, and the Church-Turing thesis says no physical device can do more.
