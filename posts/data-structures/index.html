Data Structures - Storage Is Strategy

Aug 2021
8 min read

Helpful context:

  • Big-O - Why the Right Algorithm Beats Faster Hardware

The Apollo 11 guidance computer had about 4 kilobytes of working memory, and engineers argued over individual bytes. A phone today has around two million times more. The argument hasn’t gone away. Pick the wrong data structure and code that should take seconds takes minutes, and a service built for millions of users falls over at ten thousand.

An algorithm is just a sequence of operations: look something up, insert, delete, compare. How much each one costs depends entirely on how the data is stored. The data structure decides which operations are cheap. Everything below is that one idea, applied structure by structure.

Arrays: Memory in a Line

An array stores its elements in one contiguous block of memory, side by side, with no gaps. That one fact gives you $O(1)$ access by index: the address of element $i$ is plain arithmetic.

$$\text{address}(i) = \text{base} + i \times \text{element size}$$

The same fact makes inserting in the middle expensive. There’s no gap to put the new element in, so everything after it has to shift one place right:

This is an interactive animation. It needs JavaScript to run.
nums = [12, 5, 8, 3, 9]
nums[2]            # O(1): computed address, no searching
nums.insert(1, 99) # O(n): shifts everything after index 1
nums.append(7)     # O(1) amortized: the end has room
nums.pop(0)        # O(n): shifts everything left

Arrays are also cache-friendly. A CPU never fetches one number from memory; it fetches a whole 64-byte cache line. Read element $i$ and the next several elements arrive with it, already in the fastest memory the CPU has. Walking an array in order is one of the fastest things a computer can do.

Dynamic Arrays: Amortized $O(1)$ Appends

A plain array needs its size up front. Python’s list, Java’s ArrayList and C++’s std::vector grow instead: when the array is full, they allocate one twice as large and copy everything across.

This is an interactive demo. It needs JavaScript to run.

One unlucky append copies everything. But copies only happen at sizes 1, 2, 4, 8 and so on, so across $n$ appends all the copying adds up to less than $n$:

$$1 + 2 + 4 + \cdots + \frac{n}{2} < n$$

That’s $O(n)$ total for $n$ appends, or $O(1)$ amortized each. Amortized Analysis makes this precise.

Linked Lists: Flexibility at a Cost

A linked list stores each element in its own node: the value, plus a pointer to the next node. Nodes can sit anywhere in memory; only the pointers hold the list together. So inserting doesn’t shift anything. It only rewires pointers.

This is an interactive animation. It needs JavaScript to run.

The price comes in two parts:

  • No shortcut to index $i$. You have to start at the head and follow $i$ pointers: $O(n)$.
  • Cache misses. The next node can be anywhere, so each step tends to miss the cache and wait on main memory, at roughly 100 times the cost of a cache hit. Both an array walk and a list walk are $O(n)$, but in practice a list walk is often several times slower, sometimes ten times or more. The constant hidden inside Big-O here is huge.

A singly linked list can’t delete a node on its own either, because the node before it holds the pointer that has to change, and there’s no way back to it. A doubly linked list adds a prev pointer to each node, making deletion $O(1)$ when you already hold the node.

class Node:
    def __init__(self, val):
        self.val, self.next = val, None

def prepend(head, val):   # O(1): the new node becomes the head
    node = Node(val)
    node.next = head
    return node

In Python, you almost never want to build one. Every node is a full object carrying dozens of bytes of bookkeeping. For fast operations at both ends, use collections.deque, which stores elements in blocks to avoid the per-node cost.

Stacks and Queues: Restricting Access on Purpose

Sometimes the useful thing is to allow fewer operations.

A stack is last in, first out: push on top, pop from the top. A Python list is a perfect stack, since append and pop are both $O(1)$. The most important stack in your computer is the call stack: each function call pushes a frame, each return pops one, which is why runaway recursion ends in RecursionError. Stacks also power undo, expression parsing, and checking that brackets match .

A queue is first in, first out: join at the back, leave from the front. Never use list.pop(0) for this; it’s $O(n)$, because everything shifts left. Use collections.deque, which is $O(1)$ at both ends:

from collections import deque

queue = deque(["first", "second"])
queue.append("third")
queue.popleft()      # "first", in O(1)

Queues run event loops (Node.js, asyncio), message brokers (Kafka, RabbitMQ, SQS), and breadth-first search , where the queue is exactly what makes the search go level by level.

Under the hood, and a deque trick: sliding window maximum

A stack is an array plus one integer marking the top. A queue is usually a circular array with two integers, front and back, that wrap around at the end, so nothing ever shifts.

Because a deque is $O(1)$ at both ends, it solves sliding window maximum - the maximum of every window of $k$ consecutive elements - in $O(n)$ instead of $O(nk)$. The deque keeps indices of possible maximums, largest first:

from collections import deque

def sliding_window_max(nums, k):
    dq, result = deque(), []
    for i, x in enumerate(nums):
        if dq and dq[0] <= i - k:          # front index has left the window
            dq.popleft()
        while dq and nums[dq[-1]] < x:     # smaller values can never be the max now
            dq.pop()
        dq.append(i)
        if i >= k - 1:
            result.append(nums[dq[0]])
    return result

Hash Tables: $O(1)$ by Design

A hash table finds anything by key in expected $O(1)$ time. The trick is to compute where a key lives instead of searching for it: run the key through a hash function and take the remainder by the number of buckets.

$$\text{bucket}(k) = h(k) \bmod m$$

This is an interactive animation. It needs JavaScript to run.

Two keys landing in the same bucket is a collision, and with enough keys it’s guaranteed. There are two standard fixes:

  • Chaining, as in the animation: each bucket holds a short list of everything that hashed there.
  • Open addressing: keep everything in one flat array, and on a collision probe for the next free slot. It’s friendlier to the cache, but degrades faster as the table fills.

What keeps chains short is the load factor $\alpha = n / m$, the average number of keys per bucket. Real tables keep $\alpha$ below a threshold, around 0.7, by doubling the bucket count and rehashing everything when they cross it. Like the growing array above, that occasional $O(n)$ rebuild keeps insertion $O(1)$ amortized.

“But I’ve seen hash tables take $O(n)$." Both are true. The $O(1)$ is expected, assuming a good hash function and a bounded load factor. A bad hash that sends most keys to one bucket turns every lookup into a long scan. And don’t rely on iteration order: in most hash table implementations it isn’t defined.

Priority Queues and Heaps

A priority queue always hands you the highest-priority item next, not the oldest. Insert and extract-max both run in $O(\log n)$. It’s the engine inside Dijkstra’s shortest paths and Huffman coding .

The standard implementation is a binary heap: a tree in which every parent is at least as large as its children. It’s stored as a flat array with no pointers at all - the children of index $i$ live at $2i + 1$ and $2i + 2$. Trees & Heaps builds one step by step.

Do real languages actually store arrays like this?

In C, C++, Rust and Go, and in NumPy, an array is exactly the contiguous block described above, which is why they’re fast.

Python’s list is a contiguous array of pointers: the pointers sit side by side, but the objects they point to are scattered across memory, which costs one extra hop per access. That’s also why a list can hold mixed types. Java splits the difference: int[] is raw contiguous memory, while Object[] holds references. JavaScript engines like V8 use contiguous storage while an array holds a single type, and quietly switch to something like a hash map if you mix types or leave big holes.

So in high-level languages you’re often one indirection away from the raw model, but the model is still what everything is built on, and the cache-line argument still holds.

Choosing the Right Structure

Decide by what you need to be cheap:

  • Access by position? An array.
  • Insert and delete in the middle, holding a pointer? A linked list. Check first whether an array is faster anyway, thanks to the cache.
  • Find by key? A hash table.
  • Always take the most important item next? A priority queue.
  • Keep things sorted, or ask range queries? A balanced binary search tree, where smaller keys go left and larger go right, kept shallow so every operation is $O(\log n)$.
  • Last in first out? A stack. First in first out? A queue. Both ends? A deque.

An algorithm is only as fast as the structure underneath it. Make the right operations cheap, and the algorithm often writes itself.
