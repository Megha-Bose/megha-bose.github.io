Trees & Heaps - When Flat Structures Hit Their Limit

Aug 2021
10 min read

Helpful context:

  • Data Structures - Storage Is Strategy

File systems, the browser’s DOM, a chess engine’s search, the tree of life, an org chart, the way a compiler reads (3 + 4) * 2: all trees. Trees aren’t an invention of computer science. They’re the shape hierarchical data takes on its own, whenever things have parents and children.

What Is a Tree?

A tree is a set of nodes connected without cycles, with one root. Every other node has exactly one parent and any number of children; nodes without children are leaves. In a binary tree, each node has at most two children, left and right.

class TreeNode:
    def __init__(self, val):
        self.val = val
        self.left = None
        self.right = None
  • Depth of a node: its distance from the root. Height: the longest distance down to a leaf. The tree’s height is the root’s height.
  • Complete: every level full except possibly the last, which fills left to right. Perfect: every level completely full, which means $2^{h+1} - 1$ nodes at height $h$.

The key fact: a binary tree with $n$ nodes can be as short as about $\log_2 n$ levels. Every operation that walks from the root to a node costs the height, so a short tree means $O(\log n)$ operations. Everything below is about keeping trees short.

Binary Search Trees

A binary search tree (BST) adds one rule: at every node, everything in the left subtree is smaller and everything in the right subtree is larger. To search, compare at each node and go left or right; each comparison throws away an entire subtree. It’s binary search , except the structure holds the order instead of a sorted array.

There’s a catch, and it’s easiest to see:

Feed a BST sorted keys and every new key hangs off the right of the last one. The “tree” is a linked list, and search is $O(n)$. That isn’t a rare corner case: nearly-sorted input, which is common in real data, degrades it badly too.

Deleting a node has three cases. A leaf just goes. A node with one child is spliced out, its parent linking straight to the child. A node with two children takes the key of its in-order successor, the smallest key in its right subtree, and that successor, which has at most one child, is deleted instead.

Code: BST insert and search 
class BST:
    def __init__(self):
        self.root = None

    def insert(self, val):
        if self.root is None:
            self.root = TreeNode(val)
            return
        node = self.root
        while True:
            side = "left" if val < node.val else "right"
            child = getattr(node, side)
            if child is None:
                setattr(node, side, TreeNode(val))
                return
            node = child

    def search(self, val):
        node = self.root
        while node:
            if val == node.val:
                return True
            node = node.left if val < node.val else node.right
        return False

Three Ways to Visit Every Node

  • In-order (left, node, right) visits a BST’s keys in sorted order.
  • Pre-order (node, left, right) visits a parent before its children: use it to copy or serialize a tree.
  • Post-order (left, right, node) visits children first: use it to evaluate expressions, or to free memory safely.
def inorder(node):
    if node is None:
        return []
    return inorder(node.left) + [node.val] + inorder(node.right)

Swap the order of the three pieces in that return and you get the other two. Recursion this deep can hit Python’s default limit of 1,000 frames on a degenerate tree, so production code often walks the tree with an explicit stack instead.

Code: in-order traversal with an explicit stack 
def inorder_iterative(root):
    result, stack, node = [], [], root
    while node or stack:
        while node:                 # go as far left as possible
            stack.append(node)
            node = node.left
        node = stack.pop()          # visit
        result.append(node.val)
        node = node.right           # then the right subtree
    return result

Self-Balancing Trees: AVL and Red-Black

The fix for degenerate BSTs is to rebalance after every insert and delete, using rotations: local rearrangements that change the shape but keep the left-smaller, right-larger order.

AVL trees keep every node’s two subtrees within one level of each other in height. After a change, walk back up; any node out of balance gets a single or double rotation. Here’s a right rotation fixing a tree that leans too far left:

flowchart LR subgraph before["Before: C leans left by 2"] C1["C"] --> B1["B"] B1 --> A1["A"] end subgraph after["After a right rotation"] B2["B"] --> A2["A"] & C2["C"] end

Red-black trees use a looser rule: color each node red or black, never allow two reds in a row, and give every root-to-leaf path the same number of black nodes. That caps the height at $2\log_2(n + 1)$, and needs fewer rotations than AVL, which suits write-heavy workloads. C++’s std::map, Java’s TreeMap and the Linux scheduler all use them.

flowchart TD A["7"]:::black --> B["3"]:::red & C["18"]:::red B --> D["1"]:::black & E["5"]:::black C --> F["10"]:::black & G["22"]:::black classDef black fill:#222,color:#fff,stroke:#444 classDef red fill:#c0392b,color:#fff,stroke:#c0392b

You don’t need to memorize the rotation cases. What matters is the guarantee: $O(\log n)$ search, insert and delete whatever order the keys arrive in. To watch rotations happen, try this AVL visualizer .

Python’s standard library has no balanced BST. When you need one, sortedcontainers.SortedList gives sorted order with fast inserts.

Heaps: Trees Stored in Arrays

A binary heap is a complete binary tree where every parent is at least as large as its children (a max-heap; a min-heap flips it). So the maximum is always at the root.

Because the tree is complete, it needs no pointers at all. Number the nodes level by level and store them in an array: with 0-based indexing, node $i$’s children sit at $2i + 1$ and $2i + 2$, and its parent at $\lfloor (i - 1)/2 \rfloor$. Navigating the tree is just arithmetic.

This is an interactive animation. It needs JavaScript to run.
  • Insert: put the value in the next free slot, then sift up, swapping with its parent while it’s larger. $O(\log n)$.
  • Extract-max: take the root, move the last element into its place, then sift down, swapping with its larger child while it’s smaller. $O(\log n)$.

Python’s heapq is a min-heap on a plain list:

import heapq

tasks = []
heapq.heappush(tasks, (2, "write tests"))
heapq.heappush(tasks, (1, "fix the outage"))
heapq.heappop(tasks)       # (1, 'fix the outage'): smallest first

data = [5, 3, 8, 1, 9, 2, 7]
heapq.heapify(data)        # O(n), in place

Building a heap from scratch takes $O(n)$, not $O(n \log n)$. Start at the last node that has children and sift each node down, moving toward the root. A node at height $h$ sinks at most $h$ levels, and only about $n / 2^{h+1}$ nodes have height $h$:

$$\sum_{h \geq 0} \frac{n}{2^{h+1}} \cdot h = \frac{n}{2} \sum_{h \geq 0} \frac{h}{2^h} = \frac{n}{2} \cdot 2 = n$$

Most nodes are near the bottom, where sinking is cheap, and the few near the top that can sink far are rare.

Heaps power priority queues: Dijkstra’s shortest paths always pulls the closest unvisited node next, which takes $O(V^2)$ without a heap and $O((V + E) \log V)$ with one. And heap sort is just build-heap followed by $n$ extract-maxes, each swapped to the end of the array; there’s an animation in the sorting post .

Expression Trees

A compiler turns (3 + 4) * 2 into a tree:

flowchart TD M["×"] --> P["+"] & T["2"] P --> A["3"] & B["4"]

A post-order walk evaluates it correctly: 3, 4, apply +, then 2, apply ×. The shape is the precedence; once the tree exists, the brackets aren’t needed. How Compilers Work shows a parser building one.

B-Trees: Trees for Disks

On a spinning disk, one read costs roughly 100,000 times a memory access. A balanced binary tree over a billion records is about 30 levels deep, so 30 disk reads per lookup. Far too slow.

The fix is fat nodes. A B-tree node holds many sorted keys, sized to fill one disk block, and has one more child than it has keys. With hundreds of keys per node, a billion records fit in a tree 3 or 4 levels deep: 3 or 4 reads per lookup.

flowchart TD A["10 | 20 | 30"] --> B["3 | 7"] & C["13 | 17"] & D["23 | 27"] & E["35 | 40"]

The child between keys 10 and 20 holds exactly the keys between 10 and 20: the BST rule, generalized. New keys always go into a leaf. When a leaf overflows, it splits, pushing its middle key up into the parent, and splits can cascade upward. A B-tree only grows taller when the root splits, so every leaf always stays at the same depth.

B+ trees, used by PostgreSQL, MySQL and SQLite, keep all the data in the leaves and link the leaves in a sorted chain, so a range query finds its start and then simply walks along the chain.

Code: B-tree search and insert 
class BTreeNode:
    def __init__(self, t, leaf=False):
        self.t, self.leaf = t, leaf
        self.keys, self.children = [], []

class BTree:
    def __init__(self, t):               # t = minimum degree
        self.t = t
        self.root = BTreeNode(t, leaf=True)

    def search(self, k, node=None):
        node = node or self.root
        i = 0
        while i < len(node.keys) and k > node.keys[i]:
            i += 1
        if i < len(node.keys) and k == node.keys[i]:
            return True
        return False if node.leaf else self.search(k, node.children[i])

    def insert(self, k):
        if len(self.root.keys) == 2 * self.t - 1:   # full root: split, grow taller
            new_root = BTreeNode(self.t)
            new_root.children.append(self.root)
            self._split_child(new_root, 0)
            self.root = new_root
        self._insert_non_full(self.root, k)

    def _insert_non_full(self, node, k):
        i = len(node.keys) - 1
        if node.leaf:
            node.keys.append(None)
            while i >= 0 and k < node.keys[i]:
                node.keys[i + 1] = node.keys[i]
                i -= 1
            node.keys[i + 1] = k
            return
        while i >= 0 and k < node.keys[i]:
            i -= 1
        i += 1
        if len(node.children[i].keys) == 2 * self.t - 1:
            self._split_child(node, i)
            if k > node.keys[i]:
                i += 1
        self._insert_non_full(node.children[i], k)

    def _split_child(self, parent, i):
        t, full = self.t, parent.children[i]
        right = BTreeNode(t, leaf=full.leaf)
        parent.keys.insert(i, full.keys[t - 1])     # middle key moves up
        parent.children.insert(i + 1, right)
        right.keys, full.keys = full.keys[t:], full.keys[:t - 1]
        if not full.leaf:
            right.children, full.children = full.children[t:], full.children[:t]

Tries: Trees for Strings

A trie (from retrieval) stores strings one character per edge, so words sharing a prefix share a path:

flowchart TD R["root"] --> C["c"] & D["d"] C --> CA["a"] CA --> CAT["t ✓"] & CAR["r ✓"] & CAN["n ✓"] D --> DO["o"] DO --> DOG["g ✓"]

Looking up a word of length $L$ costs $O(L)$, however many words are stored. A hash table matches that, but a trie can also find every word with a given prefix, the longest stored prefix of a string, or all words in alphabetical order. That’s autocomplete: walk down the typed prefix, then collect everything below it, in $O(L + k)$ for $k$ results.

Code: a trie with prefix search 
class TrieNode:
    def __init__(self):
        self.children = {}
        self.is_end = False

class Trie:
    def __init__(self):
        self.root = TrieNode()

    def insert(self, word):
        node = self.root
        for ch in word:
            node = node.children.setdefault(ch, TrieNode())
        node.is_end = True

    def with_prefix(self, prefix):
        node = self.root
        for ch in prefix:
            if ch not in node.children:
                return []
            node = node.children[ch]
        found, stack = [], [(node, prefix)]
        while stack:
            node, word = stack.pop()
            if node.is_end:
                found.append(word)
            for ch, child in node.children.items():
                stack.append((child, word + ch))
        return found

When Not to Use These

  • Lookups by key? A dict beats any tree.
  • Sorted data you rarely change? Sort once and use bisect for $O(\log n)$ searches on a plain list.
  • Sorted data with frequent inserts? sortedcontainers.SortedList.
  • Just the top $k$ items? heapq.nlargest(k, items). A heap shines when you keep inserting while repeatedly taking the minimum; it’s poor at removing arbitrary items or iterating in order.
