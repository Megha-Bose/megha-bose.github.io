How Compilers Work - From Source Code to Something a CPU Understands

Sep 2024
13 min read

Helpful context:

You write x = a + b * 2. The compiler works out that b * 2 happens first, may turn that multiply into a cheaper shift or add, deletes x entirely if nothing reads it, and inlines the whole thing if it sat inside a tiny function.

A compiler is, at heart, a text transformation tool. It beats most hand-written code because it’s a pipeline: a series of representations, each designed to make one kind of improvement obvious. Know the pipeline and you can predict what the compiler will do, and write code that cooperates with it.

How we got here: A-0, FORTRAN and LLVM

Before compilers, programmers wrote machine code directly: the binary encoding of every instruction, every register number. In 1952 Grace Hopper, working on the UNIVAC, built A-0, which pulled frequently used routines (square roots, logarithms, output formatting) from a catalog and stitched them together. It was closer to what we’d now call a linker than a compiler, but it established the idea of code that writes code.

The first real compiler for a high-level language is usually credited to John Backus’s team at IBM: FORTRAN, in 1957. Its radical claim was that compiled code could run as fast as an expert’s hand-written code. Most people thought that was impossible. The team proved otherwise, and compiler optimization became a field.

The next revolution was LLVM, begun in 2000 by Chris Lattner and Vikram Adve at the University of Illinois. Before it, every new language needed its own backend: instruction selection, scheduling and register allocation, written again for every CPU. LLVM offered one reusable, high-quality backend. Compile your language to LLVM’s IR, and you get every architecture LLVM supports.

Phase 1: Lexical Analysis

The lexer chops the stream of characters into tokens, the words of the language, and throws away whitespace and comments.

int x = 3 + y * 2;
→  [INT] [IDENT x] [=] [NUM 3] [+] [IDENT y] [*] [NUM 2] [;]

Each token type is a regular expression: digits make a NUM; a letter followed by letters or digits makes an IDENT. So a lexer is a finite automaton: it reads one character at a time, and its state records what it has seen so far. Tools like lex, flex and re2c combine all the token patterns into a single automaton. Production compilers such as GCC and Clang hand-write their lexers for speed and control, but the model is the same.

Phase 2: Parsing

The parser checks that the tokens follow the language’s grammar, and builds an abstract syntax tree (AST) while it does. The grammar encodes precedence in its levels, exactly as in the grammars post :

Expr   → Expr + Term | Expr - Term | Term
Term   → Term * Factor | Term / Factor | Factor
Factor → ( Expr ) | NUM | IDENT

The most common way to parse this is recursive descent: one function per grammar level, calling each other. Watch it build the tree:

Nothing in the code mentions precedence. Multiplication binds tighter simply because parse_term builds × nodes inside the call that parse_expr is waiting on, so they always end up deeper in the tree, and deeper means evaluated first.

def parse_expr(tokens):
    left = parse_term(tokens)
    while tokens.peek() in ("+", "-"):
        op = tokens.consume()
        left = BinaryOp(op, left, parse_term(tokens))
    return left

def parse_term(tokens):
    left = parse_factor(tokens)
    while tokens.peek() in ("*", "/"):
        op = tokens.consume()
        left = BinaryOp(op, left, parse_factor(tokens))
    return left

def parse_factor(tokens):
    if tokens.peek() == "(":
        tokens.consume("(")
        inner = parse_expr(tokens)
        tokens.consume(")")
        return inner
    return Leaf(tokens.consume())        # a number or an identifier

The grammar’s rule Expr → Expr + Term is left-recursive, and translated literally it would call itself forever. The while loop is the standard fix, and it’s also what makes 3 + y * 2 - 1 group as (3 + (y * 2)) - 1.

This is LL(1) parsing: it reads tokens Left to right, builds the tree top-down from the Leftmost rule, and decides each step from 1 token of lookahead. GCC, Clang and the Rust compiler all use hand-written recursive descent.

LR parsing, and why most compilers don't use it

LR parsers also read Left to right, but work bottom-up, building a Rightmost derivation in reverse: they shift tokens onto a stack and reduce groups of them to a non-terminal when a rule’s right-hand side appears on top. LR handles strictly more grammars than LL(1), but its tables are impractical to write by hand, so they’re generated by tools like yacc and bison.

The generated parser is efficient but opaque, and its error messages are notoriously unhelpful (“unexpected token at line 42”). That’s why most modern compilers prefer hand-written recursive descent with custom error recovery.

Phase 3: Semantic Analysis

Parsing answers “is this grammatical?" Semantic analysis answers “does it make sense?"

  • The symbol table maps every name to its declaration: type, scope, storage. Nested scopes are a chain of tables; looking a name up walks outward until it’s found, which is exactly how shadowing works.
  • Type checking labels every tree node with a type. In 3 + y * 2, if y is an int then y * 2 is an int, so the sum is an int. Assigning a string to an int, calling a function with the wrong number of arguments, using an undeclared name: all of these are caught here, before any code exists.
  • Type inference (Haskell, OCaml, Rust, C++ auto) works out types nobody wrote down. The classic Hindley-Milner algorithm gives every expression a fresh type variable, then solves the resulting equations by unification, matching types and propagating what’s known. It’s fast in practice, though pathological programs can make it exponential. Rust uses an extended form: in let doubled: Vec<i32> = v.iter().map(|y| y * 2).collect(); it infers the closure’s types from context.

The output is an annotated AST: every node typed, every name resolved.

Phase 4: Intermediate Representation

Compilers don’t translate the tree straight to machine code. They first lower it to an intermediate representation (IR), which is easier to analyze than either the source or machine code.

The most influential IR is LLVM IR. It looks like assembly but has infinitely many typed virtual registers. (A register is one of the CPU’s handful of tiny, ultra-fast storage slots, typically 16 to 32 on x86-64. Virtual registers get mapped onto real ones later.)

define i32 @add_mul(i32 %a, i32 %b) {
entry:
  %mul = mul i32 %b, 2     ; b * 2
  %add = add i32 %a, %mul  ; a + (b * 2)
  ret i32 %add
}

The crucial property is SSA, static single assignment: every register is assigned exactly once. Where two branches merge, a φ (phi) instruction picks a value depending on which branch was taken:

define i32 @abs(i32 %x) {
entry:
  %neg = icmp slt i32 %x, 0          ; x < 0?
  br i1 %neg, label %flip, label %done
flip:
  %negx = sub i32 0, %x
  br label %done
done:
  %r = phi i32 [ %negx, %flip ], [ %x, %entry ]
  ret i32 %r
}

Because each value has exactly one definition, every use points straight back to it. That makes many optimizations simple: a value with no uses can be deleted, and a value defined as a constant can be substituted everywhere it’s used.

Phase 5: Optimization Passes

The optimizer is a series of passes. Each reads the IR, analyzes one thing, and rewrites it. Because every pass speaks the same IR, they chain freely, and one pass’s output sets up the next:

  • Constant folding computes anything made only of constants: 4 * 8 becomes 32. If a branch condition becomes constant, the branch never taken can go too.
  • Dead code elimination deletes values nobody uses, and repeats, since each deletion can make something else unused.
  • Strength reduction swaps expensive operations for cheap ones: multiplying by 8 becomes a shift left by 3. Inside loops it also replaces i * stride with a running sum that adds stride each time round.
  • Inlining pastes a small function’s body into its caller. That removes the call overhead, and more importantly exposes the body to every other pass. Inline too much and the code bloats, so compilers use size and hotness heuristics.
  • Loop-invariant code motion hoists work that’s the same on every iteration out of the loop:
for (int i = 0; i < n; i++)
    a[i] = b[i] * (x + y);   // x + y computed n times

float xy = x + y;            // after: computed once
for (int i = 0; i < n; i++)
    a[i] = b[i] * xy;
  • Common subexpression elimination computes a repeated expression once and reuses it.
  • Alias analysis works out which pointers can’t refer to the same memory. Without it the compiler has to assume any store might change any load, which blocks reordering.

LLVM and GCC run dozens of passes, some several times, and the order matters: inlining before subexpression elimination reveals more duplicates, and dead code elimination after constant folding clears away the branches folding made dead. Tuning the order is deep compiler-engineering expertise.

Phase 6: Code Generation

The backend turns optimized IR into instructions for one particular CPU. It has three jobs.

Instruction selection picks machine instructions for each piece of IR by pattern matching. An add becomes addl; multiplying by a power of two becomes a shift; multiplying by 3 often becomes lea, an instruction designed for computing addresses that can do x + 2x in one cycle. LLVM describes these patterns in TableGen files; GCC uses RTL patterns.

Instruction scheduling reorders instructions to keep the CPU’s pipeline busy. Modern CPUs overlap many instructions at once and can run several per cycle, but an instruction that needs a result still being computed has to wait. The scheduler fills those waits with independent work.

Register allocation maps the unlimited virtual registers onto the few real ones. When too many values are live at once (still needed later), some get spilled to memory and reloaded. Two values whose lifetimes overlap can’t share a register, so this is graph coloring : one node per value, an edge wherever lifetimes overlap, one color per register. Optimal coloring is NP-hard, so compilers use heuristics. Fast JITs use linear scan, a single greedy sweep over lifetimes; GCC and LLVM color the interference graph properly for better code.

Why LLVM Changed Everything

Before LLVM, a new language needed years of backend work per CPU, which is why research languages often ran on only one or two architectures. With LLVM, a front end that emits LLVM IR gets x86-64, ARM, RISC-V, WebAssembly and more, at competitive quality.

Clang (C, C++, Objective-C; Apple’s compiler), Rust, Swift, Julia, Kotlin/Native and Emscripten (C/C++ to WebAssembly) all build on it. The languages that don’t - JavaScript’s V8, CPython, Java’s HotSpot - have poured enormous resources into their own backends, which only huge ecosystems can afford.

JIT vs AOT

Ahead-of-time (AOT) compilers like GCC, Clang and rustc run the whole pipeline before you ship. The program starts instantly, with no compilation at run time.

Just-in-time (JIT) compilers compile while the program runs. Programs spend most of their time in a small part of their code, the hot paths, so a JIT interprets everything at first, measures, and compiles only what’s hot.

  • Advantages: it can optimize for what actually happens: the real types, the branches really taken. If an assumption breaks (say, “this is always an integer”), it can deoptimize, throwing the compiled code away and falling back. That’s what makes dynamic languages fast.
  • Disadvantages: slow until warmed up, extra memory for compiled code, and only a limited time to spend optimizing.
CPython, PyPy, HotSpot, JAX and torch.compile

CPython compiles Python to bytecode (the .pyc files), compact platform-independent instructions that its interpreter executes one at a time in a big C switch. It’s simple and portable, but slow.

PyPy is a JIT for Python built with RPython, its own meta-tracing JIT framework. It finds hot loops, compiles them to machine code, and specializes them for the types it observes. CPU-bound pure-Python code often runs several times faster. It helps far less with code that spends its time inside C extensions like NumPy, which are already compiled.

Java’s HotSpot interprets bytecode at first, compiles warm methods with a quick compiler (C1), then recompiles the hottest with an aggressive one (C2). Long-running Java often gets close to C++ speed.

JAX compiles by tracing. jax.jit(f)(x) runs f on abstract tracer values that record every operation instead of computing numbers, producing a graph in XLA’s HLO IR, which XLA compiles and caches for those input shapes. There’s no lexer or parser at all; the “source” is just the operations performed. The catch: Python if statements on traced values are frozen at trace time.

torch.compile captures the Python bytecode executed during a real call (with a component called Dynamo), turns it into an FX graph of PyTorch operations, and compiles that with Inductor into optimized C++, CUDA or Triton kernels. It falls back to normal execution wherever capture fails, which makes it more forgiving than JAX, at the cost of a looser compilation boundary.

Can Machine Learning Do Better?

Classic optimizations are hand-written rules: experts decide when a transformation pays off. That works well for common code and is brittle for unusual code.

  • MLGO, used in production LLVM builds at Google, replaces the inlining heuristic with a learned policy aimed at code size, producing binaries a few percent smaller. A later policy for register-allocation choices targets speed.
  • Autotuning, used by XLA, CUDA libraries and Halide, simply benchmarks many configurations (tile sizes, loop orders) and keeps the fastest. It’s slow, but it finds settings no rule would.

So far, ML beats heuristics on specific decisions without replacing whole passes. The bottleneck is training data, which means compiling huge codebases many times with different choices and measuring each result.
