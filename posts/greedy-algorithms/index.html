Greedy Algorithms - The Art of Never Looking Back

Aug 2021
7 min read

Helpful context:

  • Divide & Conquer - Small Savings That Compound

In 1956 Joseph Kruskal published a rule for connecting a set of points with the least total length of wire, in one sentence: always add the cheapest edge that doesn’t create a cycle. No lookahead, no backtracking, no view of the whole. Just a local rule, applied again and again.

And it’s provably optimal. That’s a greedy algorithm at its best. The skill isn’t being reckless; it’s recognizing the problems where the locally best choice is also globally safe, and proving it.

The Greedy Template

solution = empty
while the problem isn't solved:
    make the choice that looks best right now
    never revisit it

Why Greedy Fails

Every greedy choice closes doors. Picture hiking toward the highest summit by always stepping uphill: you get stuck on whichever peak you happened to start climbing. Reaching the true summit might need a step down first, which greedy never takes.

0/1 knapsack is the classic trap. You have a bag that holds 10 kg, and items you must take whole or not at all. Greedy takes the best value per kilogram first:

Item Weight Value Value per kg
A 6 kg $9 1.50, the best ratio
B 5 kg $7 1.40
C 5 kg $7 1.40

Greedy takes A, after which neither B nor C fits: $9, with 4 kg wasted. Taking B and C instead fills the bag exactly: $14. The best-looking first choice ruined everything after it. Dynamic programming solves 0/1 knapsack exactly, in $O(nW)$ for capacity $W$.

When Greedy Works

Greedy is correct when a problem has two properties:

  • The greedy choice property: the locally best choice belongs to some optimal solution, so it never needs undoing.
  • Optimal substructure: once that choice is made, an optimal solution to what’s left, combined with it, is optimal overall.

Proving the first is the real work, and the standard tool is the exchange argument:

  1. Take any optimal solution $OPT$ that doesn’t make the greedy choice $g$.
  2. Swap: remove whatever $OPT$ chose instead, put $g$ in.
  3. Show the result is still valid and no worse.
  4. So some optimal solution contains $g$. Repeat on the rest of the problem.

A cousin technique, greedy stays ahead, shows instead that after every step greedy’s partial solution is at least as good as any other’s. Either way, if the argument breaks - if swapping in the greedy choice can make things worse - you’ve found your counterexample, and greedy is the wrong tool.

Activity Selection: The Proof

Pick as many non-overlapping activities as possible. Greedy rule: earliest finish time first. Sort by finish time, then sweep once: $O(n \log n)$.

Why it’s right. Let $g$ be the activity that finishes first, and take any optimal schedule that doesn’t include it. Its first activity $a$ finishes no earlier than $g$. Swap $a$ for $g$: everything else in the schedule started after $a$ finished, so it still starts after $g$ finishes. The schedule stays valid with the same count, so some optimal schedule starts with $g$. Apply the same argument to everything after it.

The animation shows why the obvious alternatives fail. Shortest first can pick a short activity that straddles two longer ones and blocks both. Earliest start can grab one long activity that blocks everything else.

Fractional Knapsack: Where Greedy Is Right

Change one thing: you may take part of an item, pouring gold dust or cutting cloth. Now greedy works. Sort by value per kilogram, take the best until it runs out, then the next, and top up with a fraction of the last one. $O(n \log n)$.

With fractions, nothing is ever wasted. Any kilogram of a lower-ratio item could be swapped for a kilogram of a higher-ratio one without loss, so the greedy order can’t be beaten. In the table above, fractional greedy takes all of A plus 4/5 of B: $9 + $5.60 = $14.60, more than any whole-item combination.

Huffman Coding: Greedy Compression

Give frequent characters short binary codes and rare ones long codes, with no code a prefix of another, so the total encoded length is as small as possible. Huffman’s rule: repeatedly merge the two least frequent nodes into a new node whose frequency is their sum. The codes are the paths from the root, 0 for left and 1 for right.

graph TB subgraph step1["Step 1: merge C(1) and B(2)"] S1R["3"] --> S1C["C: 1"] S1R --> S1B["B: 2"] end subgraph step2["Step 2: merge node(3) and D(3)"] S2R["6"] --> S2D["D: 3"] S2R --> S2N["3"] S2N --> S2C["C: 1"] S2N --> S2B["B: 2"] end subgraph step3["Final tree: merge A(5) and node(6)"] ROOT["root: 11"] --> A["A: 5\ncode: 0"] ROOT --> N6["6"] N6 --> D["D: 3\ncode: 10"] N6 --> N3["3"] N3 --> C["C: 1\ncode: 110"] N3 --> B["B: 2\ncode: 111"] end

The most frequent character, A, gets a 1-bit code; the two rarest, C and B, share the longest. Merging the two rarest first is always safe: some optimal code makes them siblings at the deepest level. With a min-heap that’s $O(n \log n)$. Huffman coding sits inside DEFLATE, which is inside ZIP, PNG and gzip, as well as JPEG and MP3. Huffman Coding builds a full tree.

Kruskal’s Minimum Spanning Tree

Connect every vertex using edges of the smallest total weight, without cycles. Sort the edges by weight, and add each one unless it would close a cycle:

graph LR A ---|"1 ✓"| B C ---|"2 ✓"| D A ---|"3 ✓"| C B -.-|"4 ✗ cycle"| D B -.-|"5 ✗ cycle"| C D ---|"6 ✓"| E

A–B (1), C–D (2) and A–C (3) go in. B–D (4) and B–C (5) would close cycles, so they’re skipped. D–E (6) completes the tree: 4 edges, total weight 12.

Why it works is the cut property: for any split of the vertices into two groups, the cheapest edge crossing between them belongs to some minimum spanning tree. Cycle checks use Union-Find . Sorting dominates: $O(E \log E)$.

Dijkstra Is Greedy Too

Dijkstra’s shortest-path algorithm repeatedly finalizes the unfinished vertex with the smallest known distance. The greedy choice property: with non-negative edge weights, no later path can beat that distance, since any detour only adds length. A negative edge breaks the property, which is exactly why Dijkstra fails with negative weights. With a binary heap it’s $O((V + E) \log V)$.

Summary

Problem Greedy rule Correct? Time Why
Activity selection Earliest finish Yes $O(n \log n)$ Exchange argument
Fractional knapsack Best value per weight Yes $O(n \log n)$ Fractions waste nothing
0/1 knapsack Best value per weight No $O(nW)$ by DP Whole items can block better combinations
Huffman coding Merge the two rarest Yes $O(n \log n)$ Rarest pair are deepest siblings
Kruskal’s MST Cheapest edge without a cycle Yes $O(E \log E)$ Cut property
Dijkstra Closest unfinished vertex Yes, if no negative weights $O((V + E)\log V)$ Detours only add length
Travelling salesman Nearest unvisited city No - Early choices force bad later ones

When you’re tempted by a greedy rule, try the exchange argument first. If it goes through, you have a proof. If it breaks, the place where it breaks is your counterexample.
