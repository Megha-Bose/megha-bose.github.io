Branch and Bound - Exhaustive Search, Intelligently Pruned

Aug 2021
5 min read

Helpful context:

  • Dynamic Programming - Never Solve the Same Problem Twice
  • Constraint Satisfaction - Searching Smart, Not Exhaustively

An airline has 200 planes, thousands of possible routes, and a fuel cost for every pairing. Which assignment is cheapest? You can’t send 0.7 of a plane anywhere, so this is an integer problem, and trying every assignment is hopeless. Allowing fractions makes it easy to solve, but the answer might put half a plane on one route and 1.3 on another.

Branch and bound is the engine inside Gurobi, CPLEX and every major optimization solver. It doesn’t improve the worst case, but it routinely finds the exact optimum far faster than brute force, because it can prove that huge regions of the search space can’t contain the answer, without ever visiting them.

The Core Idea

Picture every possible solution as a leaf of a tree. Each internal node is a partial decision: some variables fixed, the rest still free.

  • Branch: split a node by fixing one more variable, such as “item 3 in” or “item 3 out”.
  • Bound: for each node, compute the best value anything in its subtree could possibly reach: an upper bound when maximizing, a lower bound when minimizing.
  • Prune: keep the best complete solution found so far, the incumbent. If a node’s bound can’t beat it, discard the entire subtree unseen.

The search proves 90 is optimal after expanding 13 of the 31 nodes in the full tree. On real problems with hundreds of variables, that ratio becomes astronomical.

Bounds: The Whole Game

Branch and bound is exactly as good as its bound. A bound must be:

  • Valid: never more optimistic than the truth allows. An invalid bound can prune the real optimum and return a wrong answer.
  • Tight: close to the true best. “At most infinity” is always valid and never prunes anything.
  • Fast: it’s computed at every node.

The classic sources:

  • Relaxation: drop the hard constraint and solve what’s left. For knapsack, allowing fractions of items gives the bound in the animation: take whole items in order of value per kilogram, then a fraction of the next. For integer programs generally, dropping integrality gives a linear program, and LP relaxation is the workhorse of modern solvers.
  • Lagrangian relaxation: move awkward constraints into the objective as penalties. Easier to solve, usually looser.
  • Combinatorial bounds: for the travelling salesman, a minimum spanning tree of the cities is a lower bound on any tour, since deleting one edge from a tour leaves a spanning tree.

Exploring the Tree

BranchAndBound(problem):              // minimizing
    incumbent = +infinity
    queue = {root}
    while queue is not empty:
        node = take a node from queue
        if Bound(node) >= incumbent: continue          // prune
        if node is a complete solution:
            incumbent = min(incumbent, node.value)
        else:
            for child in Branch(node):
                if Bound(child) < incumbent: add child to queue
    return incumbent

The order you take nodes in is a real choice:

  • Best-first (a priority queue by bound) always expands the most promising node, so it tightens the incumbent fast and prunes the most, but it may hold a huge frontier in memory.
  • Depth-first, as in the animation, dives to a complete solution quickly and needs memory only for one path. It works best with a good heuristic for which branch to try first.

Travelling Salesman

Find the shortest tour visiting every city once. It’s NP-hard, yet branch and bound solves instances with hundreds of cities exactly. Branch on edges, “this edge is in the tour” versus “it isn’t”, and bound with the cost of the fixed edges plus a minimum spanning tree over what’s left. Stronger bounds, like 1-trees (a spanning tree plus the two cheapest edges at one city) with penalties tuned by Lagrangian relaxation, prune far more, and they’re the heart of serious TSP solvers.

“Isn’t this just backtracking?" Both search a tree, but backtracking only prunes when a constraint is actually broken. Branch and bound also prunes branches that are perfectly legal but provably no better than what you’ve already found. With tight bounds that removes almost everything. Industrial solvers add cutting planes, extra constraints that tighten the relaxation without excluding any integer solution. This combination, branch and cut, is why solvers handle problems with millions of variables.

Compared With Other Approaches

Greedy Dynamic programming Branch and bound
Always optimal? Only for some problems Yes, where it applies Yes
Worst case Polynomial Polynomial or pseudo-polynomial in the state count Exponential
In practice Very fast Fast Often fast, with good bounds
Needs The greedy choice property Optimal substructure, few states A good bound
Memory Little One entry per state One path (depth-first) up to the whole frontier (best-first)

DP needs a small set of states. Branch and bound works for any discrete optimization problem, and its speed rides entirely on the bound.

Summary

Piece Role Requirement
Branching Split into subproblems Together they must cover every solution
Bounding Best value reachable in a subtree Valid always; tight to prune well
Pruning Discard subtrees that can’t win A good incumbent, found early
Best-first order Most promising node next Prunes more, uses more memory
Relaxation A bound from an easier problem Tight for many combinatorial problems

Branch and bound always returns the true optimum. Its worst case is exponential, but with good bounds, real scheduling, routing and allocation problems are solved exactly every day.
