Searching Algorithms - Twenty Steps Through a Million Entries

Aug 2021
8 min read

Helpful context:

  • Sorting Algorithms - How Order Turns Hard Problems Easy
  • Trees & Heaps - When Flat Structures Hit Their Limit

A phone book has a million entries. Read it from the first page and you may need a million comparisons. Open it in the middle, keep the half that can hold the name, and repeat, and you never need more than 20.

That’s a 50,000-fold speedup from changing the approach, not the hardware. The gap between $O(n)$ and $O(\log n)$ is one of the most consequential in computing. But binary search is more than a lookup trick. It’s a way of reasoning that works far beyond sorted arrays, and that’s the real subject of this post.

Linear Search: When You Have No Choice

In an unsorted array there’s nothing to exploit, so you check every element: $n/2$ comparisons on average when the target is there, $n$ when it’s last or missing. Without preprocessing, nothing does better.

For tiny arrays, roughly 16 elements or fewer, a plain scan often beats binary search in practice anyway: it’s branch-predictable and cache-friendly, with no midpoint arithmetic. That’s the same reason real sort routines finish small pieces with insertion sort.

Binary Search: An Invariant, Kept Mechanically

On a sorted array, keep one promise: if the target is anywhere, it’s between lo and hi. Look at the middle. Whatever you see there lets you discard half the range without breaking the promise.

This is an interactive animation. It needs JavaScript to run.
BinarySearch(A, target):
    lo, hi = 0, n - 1
    while lo <= hi:
        mid = lo + (hi - lo) / 2
        if A[mid] == target:  return mid
        if A[mid] < target:   lo = mid + 1     // target can't be at mid or left of it
        else:                 hi = mid - 1     // target can't be at mid or right of it
    return -1                                  // range empty: not present

Each step halves the range, so after $k$ steps $n / 2^k$ candidates remain: $O(\log n)$ in total.

Binary search is famously easy to describe and hard to get exactly right. Jon Bentley found that around 90% of professional programmers he tested couldn’t write a correct one, and Knuth notes that the first binary search was published in 1946 but the first bug-free version not until 1962. Two traps:

  • The midpoint. (lo + hi) / 2 overflows when both are large; lo + (hi - lo) / 2 can’t. This exact bug sat in Java’s standard library for about nine years before it was found in 2006.
  • Off-by-one. The loop test, the + 1 and the - 1 must agree with each other. Write lo = mid instead of lo = mid + 1 and the loop can spin forever once two elements remain. The cure is to derive every update from the invariant instead of guessing.

lower_bound and upper_bound

Often you don’t want an occurrence. You want where things go:

  • lower_bound: the first index whose value is $\geq$ target. It’s also where to insert the target to keep the array sorted.
  • upper_bound: the first index whose value is $>$ target.

Every copy of the target lies in [lower_bound, upper_bound). Pick the last two cases in the animation above to watch both find the run of 3s.

LowerBound(A, target):
    lo, hi = 0, n            // hi = n: the answer might be "at the end"
    while lo < hi:
        mid = lo + (hi - lo) / 2
        if A[mid] < target:  lo = mid + 1
        else:                hi = mid        // mid might be the answer: keep it
    return lo

The invariant now is that everything before lo is less than the target, and everything from hi onward isn’t. When the two meet, that meeting point is the answer. Python’s bisect_left and bisect_right are exactly these two functions.

Binary Search on the Answer

Here’s where binary search turns into a design technique. Many problems ask for the smallest value that works, where “works” is monotone: once it’s true, it stays true for every larger value. Then you don’t need an array at all. Search over the possible answers, and test each guess:

SmallestThatWorks(lo, hi, works):
    while lo < hi:
        mid = lo + (hi - lo) / 2
        if works(mid):  hi = mid        // mid works: answer is mid or smaller
        else:           lo = mid + 1    // mid fails: answer is bigger
    return lo
  • Shipping packages. Ship all packages, in order, within $D$ days. What’s the smallest daily capacity that works? Checking one capacity is a single greedy pass, and if capacity $c$ works, so does $c + 1$. Binary search the capacities between the heaviest package and the total weight: $O(n \log S)$, where $S$ is the total.
  • Integer square root. The largest $m$ with $m^2 \leq n$, with no floating point: binary search $m$ over $[0, n]$.

Bisection and Newton’s Method: Searching for a Root

The same halving finds where a continuous function crosses zero. Bracket the root between a point where $f$ is negative and one where it’s positive, test the midpoint, and keep the half where the sign changes. This is bisection. Each step halves the bracket, so reaching precision $\varepsilon$ from a starting width $L$ takes $\log_2(L / \varepsilon)$ steps: about 3.3 more steps for every extra decimal digit. Slow, but it can’t fail.

Newton’s method uses more information. Standing at $x_n$, it knows the height $f(x_n)$ and the slope $f'(x_n)$. Pretend the curve is the straight line through that point with that slope, and jump to where the line hits zero:

$$x_{n+1} = x_n - \frac{f(x_n)}{f'(x_n)}$$

Close to a root, a smooth curve really is nearly straight, and the error of that straight-line guess shrinks with the square of the distance. So the number of correct digits roughly doubles every step. For $\sqrt{2}$, take $f(x) = x^2 - 2$; the update simplifies to $x_{n+1} = \tfrac{1}{2}(x_n + 2 / x_n)$:

Newton can fail, though. It needs a starting guess near the root, a non-zero slope at the root, and a smooth function; otherwise it can overshoot, oscillate, or land on the wrong root. Robust root-finders like Brent’s method combine both: Newton-style steps for speed, falling back to bisection whenever a step misbehaves.

Interpolation Search: $O(\log \log n)$ on Uniform Data

If the values are spread evenly, don’t probe the middle: probe where the target should be. Looking for 900 in values running from 0 to 1,000? Look about 90% of the way in.

$$\text{probe} = \text{lo} + \left\lfloor \frac{(\text{target} - A[\text{lo}])(\text{hi} - \text{lo})}{A[\text{hi}] - A[\text{lo}]} \right\rfloor$$

On uniform data that takes $O(\log \log n)$ comparisons on average, barely more than constant. On skewed data the estimate can be wildly off, and the worst case is $O(n)$. Use it for big sorted tables of roughly uniform integers like timestamps or sequential IDs, and binary search everywhere else.

Exponential Search: When $n$ Is Unknown

When the array is huge or unbounded, or the target is probably near the front, check positions 1, 2, 4, 8, … until you overshoot, then binary search the last gap:

flowchart LR A["i = 1: too small"] --> B["i = 2: too small"] --> C["i = 4: too small"] --> D["i = 8: overshot"] --> E["binary search 4..8"]

If the target sits at index $k$, both phases take $O(\log k)$, so you pay for how far in the target is, not for how big the array is.

Why You Can’t Beat $\log n$

Searching a sorted array by comparisons has $n + 1$ possible outcomes: one of $n$ positions, or “not present”. Each comparison has two outcomes, so telling $n + 1$ cases apart takes at least $\log_2(n + 1)$ comparisons. Binary search meets that bound exactly; it’s optimal.

Search in Trees and Hash Tables

  • A balanced BST also searches in $O(\log n)$, but every step follows a pointer that may miss the cache. For data that doesn’t change, a sorted array with binary search is usually several times faster.
  • A hash table doesn’t search at all: compute the hash, go to the bucket, $O(1)$ expected. Unless you need ordering or range queries, it wins.

The rule of thumb: static data, sort it once and binary search; changing data that needs ordering, a balanced BST; everything else, a hash table.
